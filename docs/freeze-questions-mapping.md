# 지난 글의 세 질문 → 이 저장소의 구현 매핑

출처: 지난 LinkedIn 글 「스테이블코인의 동결 권한을 코드로 읽으면 무엇이 빠져 있을까?」 —
USDT · USDC 공개 컨트랙트 코드와 BitOK 의 동결 회피 분석을 읽고 정리한 내용.

> 이 문서는 **공개 컨트랙트 코드에서 읽은 구조** 를 바탕으로 한다. Tether · Circle 의 내부 운영
> 절차(오프체인 검토, 수사기관 협조 방식 등)는 알 수 없고, 여기서 다루지 않았다.
> 구현은 "이렇게 해야 한다" 는 제안이 아니라, 절차를 코드에 넣을 때 **어디서 어긋나기 쉬운지** 를
> 보려고 만든 최소 예제다.

## 지난 글에서 찾은 것 전체

| 질문 | 지난 글에서 읽은 것 | 이 저장소 |
|---|---|---|
| ① 동결과 몰수의 거리 | USDT 에는 `destroyBlackFunds` 가 있어, 동결과 같은 권한자가 바로 소각까지 할 수 있다 | ❌ 미구현 |
| ② 사유 기록 | 동결 이벤트는 `AddedBlackList(address)` / `Blacklisted(address)` — 주소 하나가 전부 | ✅ `02-zk-reason` (사유 봉인 + 목록 소속 증명) |
| ③ 대기 시간 | 멀티시그 제안이 서명을 기다리는 동안 공개되어, 그 틈에 자금이 먼저 빠져나감 (BitOK: 100건+, 3천만 달러+ 추정) | ✅ `01-pending-leak` (커밋-리빌) |

①을 뺀 이유: 몰수를 동결과 분리하려면 **역할 분리 + 시간 지연 + 이의제기** 가 함께 들어가야 하는데,
이건 ③의 "유예 기간은 양쪽에 똑같이 주어진다" 는 균형 문제와 얽혀 있어서 논문에서 따로 다루려 한다.

## 22회차 "금고 3분류" 프레임과의 대응

| 문제 | 금고 3분류 | 어긋나는 지점 |
|---|---|---|
| 대기 중인 제안 노출 | ① 문지기 (권한) | 권한 행사 **예고** 가 공개 신호가 됨 |
| 사유 확인 불가 | ① 문지기 (권한) | 권한 행사의 **근거** 가 저장·검증되지 않음 |
| 증명이 대상에 안 묶임 | ② 외부의 문 (호출) | 누구나 제출 가능한 입구에서 **검사 범위가 인자보다 좁음** |
| root 갱신으로 증명 무효 | ③ 내부 장부 | 검증 기준값이 **하나만 저장** 됨 |

## SEC 저장소의 세 질문과의 대응

| SEC 저장소의 질문 | 이번 저장소에서 |
|---|---|
| 어디서 세느냐 | 이번엔 해당 없음. 다만 "사유 하나로 몇 번 동결할 수 있는가" 를 세려면 nullifier 가 필요하다 (미구현) |
| 모를 때 어느 쪽으로 넘어지느냐 | root 가 바뀌어 증명을 확인할 수 없으면 **동결하지 않는 쪽** 으로 넘어진다 (fail-closed). 동결에서는 이게 안전한 쪽인지 확신이 없다 — 해커가 시간을 번다 |
| 어디에 저장하느냐 | 사유를 평문으로 저장하면 프라이버시가, 저장하지 않으면 검증이 깨진다. **봉인(commitment)으로 저장하고, 이의제기 때 연다** |

## 남은 질문

- root 히스토리를 몇 개까지 기억해야 하나? 너무 길면 철회된 사유로도 동결할 수 있게 된다.
- 레지스트라 자체를 여러 기관의 멀티시그로 두면 신뢰가 분산되는가, 아니면 01 의 대기 시간 문제가 레지스트라 쪽으로 옮겨가는가?
- 이의제기 때 `(leaf, salt)` 를 공개하는 대신, "사유가 특정 분류(예: 법원 명령)에 속한다" 만 추가로 증명하는 선택적 공개가 가능할까? (회로에 `category` 범위 검사를 추가하면 될 것 같다)
- 무고한 이용자에게 통지 기간을 줄 때, 그 기간 동안 **잔고 이동만 막고 나머지는 허용** 하는 부분 동결이 균형점이 될 수 있을까?
